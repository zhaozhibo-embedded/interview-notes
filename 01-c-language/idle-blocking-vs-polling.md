# 一次“偶发”关机失败的排查：嵌入式里的阻塞等待与轮询

> **When a Blocking Wait Never Wakes** — Debugging an Intermittent Shutdown Failure on JL701N
>
> 平台：JL701N（BR28）/ JieLi 音箱 SDK　｜　关键词：RTOS、消息队列、阻塞、轮询、软关机、低功耗复位

---

## TL;DR

一个“有时能关机、有时重启”的偶发问题，根因是 **消费者在消息队列上阻塞等待，而生产者只改了一个全局变量、没有发消息**。

改成轮询（`block = 0` + `os_time_dly(1)`）后问题消失。

顺手暴露并修掉了两个连带问题：

1. 原本永远执行不到的“3 秒超时兜底”，在改成轮询后生效了——但关机提示音实际有 3.5 秒，超时比它还短；
2. 充电待机的点灯循环有**一模一样**的阻塞写法，拔掉充电器后永远卡住。

---

## 1. 现象

同一份固件、同样的操作（板子按键 4 击关机），结果不稳定：

- 有时正常进入真待机（0.1mA）；
- 有时重启一次，然后落进伪待机（CPU 不睡）。

“偶发”两个字很关键：说明存在一个**竞态**，而不是逻辑写错。

---

## 2. 背景：两套待机

产品里有两套待机流程，在 idle 任务里根据一个 RAM 标记分流：

| 触发 | 待机方式 | 特点 |
|---|---|---|
| 按键长按 | 伪待机 | CPU 不睡，433 接收常开，遥控可唤醒 |
| 按键 4 击 | 真待机 | `power_set_soft_poweroff()`，≈0.1mA，只能按键/充电唤醒 |

真待机流程大致是：

```
按键 4 击 → 置标记 → 正常关机流程 → 进 idle 任务
        → 播关机提示音 → 等提示音播完 → 关外设 → power_set_soft_poweroff()
```

问题出在“**等提示音播完**”这一步。

---

## 3. 日志证据

失败的一次：

```
11.499  [IDLE] poweroff tone end      ← 关机音播完，回调置了“完成”标志
        ...（之后只剩 1 秒一次的心跳，没有任何业务日志）
17.304  Reset Source : P33_SOFT_RST
        LVD_FLAG: 1
        lptmr_timeout                 ← 低功耗定时器超时导致的软复位
```

成功的一次：

```
42.967  [IDLE] poweroff tone end
43.031  stack_resume_fail!!!:14       ← 一个“无关”的事件
43.530  product stone suspend         ← 这时才真正关外设
43.543  M2P_VDDIO_KEEP ...            ← 睡下去
```

两个关键点：

1. 失败时**从来没有打印** `product stone suspend` —— 说明代码根本没走到“关外设、断电”那一段。
2. 成功时多了一行 `stack_resume_fail`，它“碰巧”把 idle 任务叫醒了。

也就是说：**能不能关机，取决于有没有别的消息碰巧进来。**

---

## 4. 根因：等错了对象

出问题的循环（等关机音播完）：

```c
u32 tone_start = timer_get_ms();
while (1)
{
    app_task_get_msg(msg, ARRAY_SIZE(msg), 1);   // ← 第三个参数 1 = 阻塞

    switch (msg[0]) { /* 处理系统事件 */ }

    if (app_task_exitting()) { /* 用户按了开机键 */ return; }

    if (s_idle_poff_tone_done) { break; }        // ← 等这个标志

    if ((timer_get_ms() - tone_start) >= TIMEOUT_MS) { /* 超时兜底 */ }
}
```

`app_task_get_msg` 的原型：

```c
void app_task_get_msg(int *msg, int msg_size, int block);
```

第三个参数就叫 `block`：

- `1`：队列空了就**挂起任务**，直到有消息；
- `0`：队列空了**立刻返回**。

而“播完”的通知是这样产生的（在**音频解码任务**的上下文里执行）：

```c
static void _idle_poweroff_tone_end(void *priv, int flag)
{
    s_idle_poff_tone_done = 1;        // 只写了一个全局变量
}
```

于是：

```
解码任务：置标志 = 1，函数返回
idle 任务：阻塞在消息队列上，等消息……永远等不到
```

更糟的是，**超时兜底写在阻塞调用后面**。任务醒不过来，这行判断自然永远执行不到。

接下来的连锁反应：

1. 所有任务都不就绪 → SDK 认为系统空闲，尝试进低功耗；
2. 约 5 秒后低功耗定时器超时 → `P33_SOFT_RST` 软复位；
3. 复位清 RAM → 表示“这次要真待机”的标记丢失；
4. 重启后看到标记是 0 → 走伪待机。

成功的那次，只是碰巧有个 `stack_resume_fail` 事件进了队列，把 idle 任务唤醒。

---

## 5. 修复：阻塞改成轮询

```diff
     u32 tone_start = timer_get_ms();
     while (1)
     {
-        app_task_get_msg(msg, ARRAY_SIZE(msg), 1);
+        msg[0] = 0;
+        app_task_get_msg(msg, ARRAY_SIZE(msg), 0);   /* 0 = 不阻塞 */
 
         switch (msg[0])
         {
         case APP_MSG_SYS_EVENT:
             if (idle_sys_event_handler((struct sys_event *)(&msg[1])) == false) {
                 app_default_event_deal((struct sys_event *)(&msg[1]));
             }
             break;
         default:
             break;
         }
 
         if (app_task_exitting()) { ... return; }
 
         if (s_idle_poff_tone_done) { break; }
 
         if ((timer_get_ms() - tone_start) >= TIMEOUT_MS) { ... }
+
+        os_time_dly(1);      /* 10ms 一拍，主动让出 CPU */
     }
```

---

## 6. 逐行讲解

### `msg[0] = 0;`

`app_task_get_msg` 在 `block = 0` 且队列为空时**可能什么都不写**。`msg` 是栈上复用的数组，里面还留着上一轮的消息。不先清零，下面的 `switch (msg[0])` 会把**上一条消息再处理一遍**。

先清 0，等于告诉后面：“这一轮没有消息”。

### `app_task_get_msg(msg, ARRAY_SIZE(msg), 0);`

把 `block` 从 1 改成 0：

- 有消息：照常取出，交给 `switch` 处理；
- 没消息：立刻返回，不挂起。

循环从“**睡着等通知**”变成“**每一拍问一次**”。

### `switch (msg[0]) { ... }`

消息处理逻辑完全保留。等待关机音的这几秒里，用户可能按了开机键、可能有系统事件，这些仍然要处理。

### `if (app_task_exitting())`

保留。用户在这几秒里长按开机键，仍然能正常退出、回到开机流程。

### `if (s_idle_poff_tone_done)`

**修复的核心**。改成轮询后，这一行每 10ms 执行一次，不管标志是被哪个任务、哪个上下文置的，都能在 10ms 内看到。

### `if ((timer_get_ms() - tone_start) >= TIMEOUT_MS)`

原来这行是“永远执行不到”的死代码，现在变成真正有效的兜底：即使回调丢了，也能在超时后继续关机。

### `os_time_dly(1);`

**这一行不能省**。没有它，`while(1)` 就变成忙等：CPU 100% 跑在这个循环里，蓝牙、音频、按键扫描全被饿死，比原来的问题更严重。

`os_time_dly(1)` 让当前任务睡 1 个 tick（本 SDK 为 10ms），期间把 CPU 让给别的任务。所以这个循环的真实开销是：**每 10ms 醒一次，做几个 if 判断，再睡回去**。

---

## 7. 原理：阻塞和轮询

### 阻塞等待

任务调用一个“会等”的函数（消息队列、信号量、事件组）。条件不满足时**任务被挂起、让出 CPU**，直到条件满足被内核唤醒。

- 优点：不占 CPU；事件到达后立即响应（微秒级）。
- 前提：**你等的那个对象，必须就是事件生产者会去写的对象**。
- 危险：等错对象 = 永久挂起；而且“超时兜底”如果写在阻塞调用之后，会跟着一起失效。

### 轮询

任务不挂起，每隔固定时间主动检查一次状态。

- 优点：不依赖事件投递路径，谁改的变量都能看到；超时和状态机都好写。
- 缺点：有最长一个周期的延迟；需要周期性唤醒。
- 关键：**两次检查之间必须主动让出 CPU**（`os_time_dly` / `sleep`），否则就是忙等。

### 对照表

| | 阻塞 | 轮询 |
|---|---|---|
| 等什么 | 队列 / 信号量 / 事件 | 一个变量或状态 |
| 谁唤醒 | 内核（消息到达） | 自己（定时） |
| 响应延迟 | 微秒级 | 一个轮询周期 |
| CPU 占用 | 0 | 每周期一次检查 |
| 典型误用 | 生产者只改变量、不发消息 | 循环里不放 `os_time_dly` |

这次就是第一种误用：生产者在别的任务里**只置了一个变量**，消费者却在**消息队列**上阻塞等待。

---

## 8. 两种改法，为什么选轮询

其实有两条路：

1. **让生产者发消息**：回调里 `os_taskq_post_msg("app_core", ...)`，把 idle 任务叫醒。
2. **让消费者轮询**：`block = 0` + `os_time_dly(1)`。

选第 2 条的原因：

- 回调运行在音频解码任务里，往 app 任务投消息要处理队列满、返回值、任务名等细节，改动面更大；
- 轮询**顺带把超时兜底救活了**（第 1 种改法救不活：消息没来还是阻塞）；
- 关机流程本来就只有几秒钟，10ms 的检查周期完全够用。

## 9. 连带问题一：超时比提示音还短

改成轮询后，原本“永远不会执行”的超时兜底突然生效，于是暴露了一个隐藏的坑：

```c
#define IDLE_POWEROFF_TONE_TIMEOUT_MS   3000u
```

而实测关机音长度是 **3.5 秒**（`TONE OPEN` 到 `poweroff tone end`）。也就是说：**超时比提示音还短**，轮询一开，它会在音还没播完时抢先触发关机。

修复：改成 5000ms，给提示音留 1.5 秒余量。

> 教训：把一个“死代码”救活之前，先确认它的数值假设还成立。

---

## 10. 连带问题二：充电点灯循环

充电待机的点灯循环里有一模一样的写法：

```c
while (1)
{
    app_task_get_msg(msg, ARRAY_SIZE(msg), 1);   // 阻塞
    ...
    if (get_charge_online_flag() == 0) {         // 拔线判断
        if (++unplug_cnt >= 10) { /* 关机 */ }
    }
}
```

充电时靠“充电事件”把循环叫醒，勉强能用；**一拔线，事件没了，循环就永远卡在阻塞上**，走不到拔线判断，机器一直亮着灯不睡。

同样改成轮询，同时把防抖计数从 10 改成 100：

- 原来每拍是一次充电事件（约 250ms），10 拍 ≈ 2.4 秒；
- 现在每拍 10ms，10 拍只有 100ms，太快；100 拍 ≈ 1 秒。

---

## 11. 排查方法论

1. **先看“最后一条日志”**。失败时停在 `poweroff tone end`，成功时后面还有 `product stone suspend`——差一行，就把范围缩小到“从回调到关外设”之间。
2. **看复位源**。`P33_SOFT_RST + lptmr_timeout` 说明不是电源问题，而是系统进了低功耗又被定时器叫醒。
3. **对照成功和失败的差异**。成功那次多了一个 `stack_resume_fail`，这就是“碰巧叫醒它”的事件。
4. **找“唯一唤醒源”**。偶发问题往往不是时序，而是“有没有别的事件碰巧叫醒它”。
5. **重新审视每个阻塞点**。同一个工程里往往不止一处相同写法（这次是两处）。

---

## 12. 检查清单

写 RTOS 代码时，可以拿这份清单过一遍：

- [ ] 我阻塞等待的对象，是不是生产者真正会写的对象？
- [ ] 如果生产者只改了一个变量，那我是不是应该轮询？
- [ ] 我的超时 / 兜底逻辑，是不是写在阻塞调用**之后**（永远执行不到）？
- [ ] 轮询循环里有没有 `os_time_dly` / `sleep`？没有就是忙等。
- [ ] 轮询周期是多少？和状态变化的最快速度匹配吗？
- [ ] 救活一段“死代码”时，它的常量假设还成立吗？
- [ ] 同样的写法，工程里还有没有第二处？
